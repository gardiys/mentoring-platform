# Аудит расходов AI — 8 сентября 2026

Проверены текущие файлы проекта, включая незакоммиченные изменения, локальные настройки моделей и официальные тарифы OpenAI. Пользователь сообщил о расходе $6,40 за день. Статистика запросов и конфигурация production не получены, поэтому ниже — подтверждённые по коду источники расходов и возможности оптимизации, а не распределение сегодняшнего счёта. На момент аудита оптимизации ещё не были внедрены. Текущее состояние реализации описано в [оптимизациях расходов AI](ai-cost-optimizations.md).

В локальном `.env` extraction, analysis и light review используют `gpt-5-mini`; транскрибация — Nexara. Разделение на «лёгкую» и основную модель сейчас локально не даёт разницы в тарифе. Настройки развёрнутого сервера могут отличаться.

## Где возникают платные запросы

Все найденные прямые обращения к OpenAI сосредоточены в [intelligence_ai.py](../backend/app/interviews/intelligence_ai.py), в `OpenAIInterviewAIProvider`: девять операций генерации текста и одна операция embeddings. Восстановление некорректного ответа добавляет повторные вызовы.

| Операция | Когда выполняется | Модель / особенности | Возможность экономии |
| --- | --- | --- | --- |
| `extract` | Выделение вопросов и ответов из транскрипта | Extraction; фрагменты до 70 реплик, перекрытие 10, ограничение 60 000 символов | Сохранять каждый успешный фрагмент; возобновлять с места сбоя |
| `review` | Отдельная оценка каждого ответа | Analysis для технических вопросов, light для остальных | Исключить не требующие оценки организационные ответы; сократить необязательный вывод после проверки качества |
| `summarize` | Общий итог интервью | Light; до 20 блоков оценок / 45 000 символов в запросе; при нескольких частях дополнительное обобщение | Сохранять промежуточные итоги; сокращать повторяющиеся данные, сохраняя доказательства выводов |
| `route_question` | Классификация вопроса для автоматизации карточек | Light; вопрос, ответ кандидата, контекст, доступные темы | Доверенное точное совпадение проверять до AI при соблюдении фильтров качества; улучшить кеш |
| `judge_card_match` | Проверка смыслового совпадения с существующей карточкой | Light; вызывается для лучшего подходящего кандидата | До AI проверять условия, из-за которых совпадение всё равно будет отклонено |
| `generate_answer_contract` | Подготовка ответа для кластера будущей карточки | Analysis; до 8 источников по 8 000 символов | Переиспользование готового ответа уже есть; передавать релевантные отрывки источников |
| `validate_answer_contract` | Независимая проверка ответа по источникам | Analysis; повторно получает источники и ответ | Кеш и отрывки; сохранить независимую проверку перед публикацией |
| `embed` | Векторы вопросов, карточек и подтверждённых формулировок | По умолчанию `text-embedding-3-small`, 256 измерений | Кеш уже есть; дополнительно объединять одинаковые тексты до отправки |
| `generate_career_package` / `assess_employment_profile` | Карьерные материалы и оценка трудоустройства | Две отдельные операции на light-модели | Для карьеры кеш уже есть; для трудоустройства добавить кеш по содержимому и учёт токенов |

В последней строке таблицы объединены две операции. Повторный запрос восстановления — дополнительный путь расходов внутри `review` и `summarize`.

Nexara оплачивается отдельно от OpenAI: [intelligence_providers.py](../backend/app/interviews/intelligence_providers.py). Добавленный `telephonic` не создаёт дополнительного запроса. Добавленный словарь в [intelligence_transcript_context.py](../backend/app/interviews/intelligence_transcript_context.py) увеличивает существующие запросы извлечения и оценки, но отдельного вызова модели не добавляет. Технический словарь можно исключить из оценок организационных и HR-вопросов, сохранив правила интерпретации речи.

В интеграции Copilot в этом репозитории прямых вызовов OpenAI не найдено. Расходы отдельного сервиса Copilot, если он использует тот же OpenAI-проект, по этому коду определить нельзя.

## Подтверждённые места лишней работы

**1. При сбое может повторяться уже оплаченная обработка фрагментов.** В `extract_interview_structure` результаты и usage складываются в списки и сохраняются после завершения всех запросов. Если поздний фрагмент падает, успешные предыдущие фрагменты не сохранены и при повторе оплачиваются снова. Похожая ситуация с промежуточными summary. Решение: кеш/контрольная точка по фактическому входу, модели, версиям промпта и схемы, направлению и версии разметки говорящих; итоговые вопросы публиковать атомарно после сборки всех частей. Код: [intelligence_jobs.py](../backend/app/interviews/intelligence_jobs.py).

Это не относится ко всем повторам одинаково: уже существующие оценки ответов пропускаются. При обработанной AI-ошибке `_record_failure` коммитит накопленные оценки. Однако аварийное завершение воркера до коммита может потерять и их. Не следует описывать обычный retry как безусловный полный повтор интервью.

**2. Восстановление ответа заново выполняет всю оценку.** `_parse_user_facing_response` повторяет запрос при неверной структуре, обрезанном ответе или нерусском тексте. Лимит вывода при этом растёт с 4 000 до 8 000 токенов. В usage попадает только возвращённый успешный ответ; первая попытка теряется. При устойчивой retryable-ошибке отдельная оценка может дойти до двух вызовов на каждой из четырёх попыток задачи. Нужны раздельные счётчики причин, общий бюджет восстановления и сохранение usage каждой попытки. Для пригодного структурированного ответа с проблемой языка стоит проверить отдельное исправление нужного поля вместо повторной оценки. Схему и проверку качества сохранять. Код: [intelligence_ai.py](../backend/app/interviews/intelligence_ai.py), `_parse_user_facing_response`.

**3. AI-классификация предшествует точному совпадению.** `process_question_occurrence` сначала вызывает `_route`, затем ищет готовую карточку или подтверждённую формулировку. Для повторяющихся вопросов это потенциально лишний запрос. Быстрый путь должен использовать доверенные формулировки того же направления и сохранять проверки пригодности вопроса, уверенности извлечения, контекста и прав доступа. Простая перестановка без этих проверок может ухудшить качество. Код: [card_automation_pipeline.py](../backend/app/interviews/card_automation_pipeline.py).

**4. Проверка разницы между похожими кандидатами стоит после AI-судьи.** В семантической ветке минимальный score проверяется заранее, а score gap — уже после `judge_card_match`. Если обязательное условие заведомо не выполнено, запрос можно пропустить и продолжить существующую ветку кластеризации. Аналогично для остальных независимых от AI условий. Изменится полнота диагностического протокола, поэтому следует записывать причину пропуска. Код: `process_question_occurrence` и [card_automation_domain.py](../backend/app/interviews/card_automation_domain.py), `match_gate`.

**5. Ключи кеша учитывают текст, который модель не получает.** В `_route` и `_cached_or_judged_match` hash считается до обрезки вопроса, ответа и контекста. Два одинаковых фактических запроса с различием только в отброшенном хвосте дают разные ключи. Нужно сначала сформировать окончательный безопасный payload, затем использовать его и для hash, и для отправки. Включать модель, промпт, схему и нужную область доступа. Совпадение только вопроса недостаточно: ответ и соседние реплики могут менять смысл и пригодность карточки.

**6. Источники отправляются крупными блоками.** `_trusted_sources` выбирает до восьми материалов, ранжирует их по словам в названии/описании, затем берёт первые 8 000 символов каждого. Генерация и независимая валидация могут получать до 64 000 символов источников каждая. Поиск содержательных отрывков с сохранением source ID способен уменьшить вход и повысить релевантность. Не стоит просто уменьшать число источников без проверки покрытия темы. Код: [card_automation_jobs.py](../backend/app/interviews/card_automation_jobs.py).

## Что можно удешевить без замены модели

Для `gpt-5-mini` опубликованы следующие тарифы за миллион токенов:

| Режим | Вход | Кешированный вход | Выход, включая reasoning |
| --- | ---: | ---: | ---: |
| Standard | $0,25 | $0,025 | $2,00 |
| Batch | $0,125 | $0,0125 | $1,00 |
| Flex | $0,125 | $0,0125 | $1,00 |

Источник: [официальные тарифы OpenAI](https://developers.openai.com/api/docs/pricing), проверены 8 сентября 2026. Фактическая сумма зависит от выбранного режима и условий аккаунта.

**Batch для старых 1 300+ вопросов.** Скидка 50% относительно синхронной обработки; заявленное окно выполнения одного batch — до 24 часов. Сохраняются модель, промпты и проверки. Для цепочки зависимых этапов понадобятся отдельные партии, поэтому весь процесс может занять больше суток. Нужны сохранение batch ID, сопоставление результата с вопросом/ревизией, отмена применения устаревших результатов и повтор только неуспешных элементов. Это отдельная интеграция: нынешние пакеты embeddings по 64 текста не являются OpenAI Batch API. [Документация Batch](https://developers.openai.com/api/docs/guides/batch).

**Flex для фоновых запросов.** Те же сниженные тарифы, обычный Responses API с `service_tier="flex"`. Ответы могут приходить медленнее; возможен `429 Resource Unavailable`, за который OpenAI не берёт плату. Текущий локальный таймаут OpenAI — 120 секунд, поэтому включать Flex одной строкой опасно для надёжности: нужно согласовать таймауты API и воркера, повторы и явное правило перехода на Standard. Автоматический переход на обычный тариф уменьшит экономию. [Документация Flex](https://developers.openai.com/api/docs/guides/flex-processing).

**Prompt caching.** У OpenAI он работает автоматически; отсутствие специальных параметров не означает, что кеша нет. Стабильные инструкции и схема должны быть общим префиксом, переменные данные — после них. Измерять `cached_tokens` прежде, чем менять раскладку промпта. Это скидка на входной префикс, а не кеш готового ответа и не скидка на весь запрос. [Документация кеширования](https://developers.openai.com/api/docs/guides/prompt-caching).

Для понимания масштаба: 1 300 запросов по 1 000 выходных токенов на Standard `gpt-5-mini` стоят $2,60 только за выход. Это условный пример, не реконструкция расхода $6,40: неизвестно, сколько вопросов обрабатывалось сегодня и какие операции выполнялись.

## Изменения, которым нужна проверка качества

- Проверить меньший `reasoning.effort` сначала на классификации и сопоставлении. Сейчас явно `low` задан только для карьерного пакета. Reasoning оплачивается как выход; уменьшение effort может уменьшить расход, но эффект на качество надо измерять. Не переносить настройку автоматически на сложную техническую оценку. [Документация reasoning](https://developers.openai.com/api/docs/guides/reasoning).
- Сохранять организационные вопросы про дату выхода и условия, но не генерировать для них полный учебный разбор. Это изменение продукта, которое убирает именно эту оценку. HR-вопросы про опыт и мотивацию могут требовать содержательной обратной связи.
- Ограничить объём пояснений и «улучшенного ответа» там, где кандидат уже ответил полно. Учесть зависимость: `suggested_better_answer` уже используется для черновика ответа кластера. Если перестать генерировать его в интервью, новая генерация карточки может вернуть часть расходов.
- Не уменьшать вслепую `max_output_tokens`: это верхний предел, а не обязательный расход. Обрезанный JSON запускает восстановление и способен сделать обработку дороже.
- Не удалять перекрытие фрагментов и контекст перебиваний: они нужны, чтобы отделить ответ кандидата от реплик и подсказок интервьюеров. Сохранять независимую проверку ответа для общей базы карточек.

Для проверки собрать фиксированную выборку повторяющихся вопросов, длинных ответов, отрицаний, Python/Go-терминов, нескольких интервьюеров и перебиваний. Сравнить пропуски вопросов, неверное авторство реплик, оценки кандидата и ложные связи с карточками; отдельно измерять токены, повторы и цену. Уверенность, заявленная самой моделью, не заменяет эту проверку.

## Что уже экономит и не требует повторной реализации

- Детерминированные фильтры исключают очевидный шум и уверенно распознанные HR/организационные вопросы из платной маршрутизации карточек.
- Для маршрутизации, AI-судьи, генерации и валидации ответов уже существуют кеши.
- Готовые оценки пропускаются; общий итог повторно не генерируется, если уже существует.
- Ответ кластера может строиться из имеющегося разбора интервью без нового запроса генерации. При отсутствии источников AI-валидация не запускается.
- Embeddings обновляются только для отсутствующих/устаревших записей. Загрузка каталога из БД сама по себе не означает повторную платную генерацию всех векторов. Дополнительная дедупликация одинакового текста возможна, но это ниже по приоритету: стандартный тариф `text-embedding-3-small` — $0,02 за миллион входных токенов. [Тарифы](https://developers.openai.com/api/docs/pricing).
- Карьерный пакет уже защищён от параллельного запуска и повторной генерации одинакового компонента по тем же исходным данным. Локально автоматическая генерация после финального резюме выключена. Код: [career_packages/service.py](../backend/app/career_packages/service.py), `request_generation`.
- Периодический reconciler работает с незавершёнными задачами; наличие cron само по себе не подтверждает бесконечный платный переразбор готовых карточек.

## Почему текущий учёт не объясняет счёт

`IntelligenceAIUsage` хранит успешные операции интервью; `AutomationDecision` — токены и оценку стоимости автоматизации; карьерный пакет — `token_usage` успешного запуска. В [employment_qualification/jobs.py](../backend/app/employment_qualification/jobs.py) usage результата вообще не сохраняется.

Первая попытка восстановления, некоторые успешные фрагменты перед сбоем, невалидные ответы и ответы, отброшенные из-за смены ревизии, могут не попасть в учёт. `AIUsageResult` не сохраняет раздельно cached input и reasoning: reasoning входит в общий `output_tokens`, но его долю сейчас не видно. Тарифы `OPENAI_*_PRICE_PER_MILLION_USD` по умолчанию равны нулю, и тогда стоимость решения становится `None`. Метрики автоматизации суммируют только `AutomationDecision.cost`, а не все расходы платформы.

Нужен общий журнал вызовов на уровне провайдера: операция, модель и фактический service tier, request ID, сущность/ревизия, вход/кешированный вход/выход/reasoning, статус, причина повтора и оценка стоимости по версии тарифа. Записывать usage до проверки результата и независимо от применения к бизнес-объекту; неизвестный расход при сетевой неопределённости не считать нулём. Сверять журнал с OpenAI Usage/Costs отдельно по production-проекту. Удаление интервью не должно удалять финансовые агрегаты: текущая таблица usage связана с интервью через `ON DELETE CASCADE`.

Лимиты количества запусков и параллельности не являются лимитом долларов. Для контроля расходов нужен бюджет фонового запуска и дня, с учётом уже выполняющихся запросов. Массовую обработку можно приостанавливать на границе бюджета с сохранением результатов; замедление очереди само по себе не снижает итоговую цену.

**Порядок внедрения:** сначала журнал расходов, исправление ключей кеша и сохранение успешных фрагментов; затем пропуск заведомо ненужного AI-судьи и безопасный путь точных совпадений; после этого Flex/Batch для фоновой обработки. Изменения reasoning, объёма разбора и отбора источников — после сравнительной проверки качества. Общий процент экономии без статистики запросов и доли повторов не установлен.
