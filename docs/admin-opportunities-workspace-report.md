## Сопутствующее исправление отправки email

При запросе кода подтверждения в заявке Python → Go Brevo отклонял письма:

1. `missing_parameter`: передавалось пустое имя получателя. Теперь необязательное
   поле `name` отсутствует, если имя пустое.
2. `out_of_range`: ключ идемпотентности имел вид `legal-<UUID>`. Теперь используется
   UUID записи доставки, одинаковый при повторных попытках.

В локальном окружении worker перезапущен. После исправлений Brevo принял одно из
ранее запрошенных писем при штатной повторной попытке; запись перешла в `sent`.
Это подтверждает приём провайдером, а не получение письма почтовым клиентом.
Тест подтверждения email проверяет оба ограничения запроса, прохождение очереди
и последующее подтверждение кода. Письма с PDF-офертой также проверяют формат UUID.

### Решения по пограничным случаям

1. Попытка в `manual_review` имеет приоритет перед более новой pending-попыткой.
   Иначе оплата старой ссылки снова исчезала бы из очереди проверки — это именно
   сценарий из исходного ревью. После ручного подтверждения остальные pending-ссылки
   отзываются; подтверждённая попытка показывается в карточке оплаты.
2. Продление Go очищает принятие прежних условий, чтобы старое согласие не применялось
   к заново зафиксированному предложению. Цена и финансовые формулы берутся из
   существующего каталога; state machine повтора Python не менялась.
3. Уведомление ментора в колокольчике хранит пустой `action_url`. Сервис принимает
   явное отсутствие ссылки; интерфейс уже умеет показывать такие уведомления без перехода.
4. Выбор ментора из старой заявки не восстанавливается догадками. Если в прежней истории
   его нет, показываются назначенный ментор и известные события; новые заявки сохраняют выбор.

Приняты решения по умолчанию из раздела 10 ТЗ: ручной возврат с явным выбором,
личные сообщения администраторам, контакты ученика ментору, сводка в 10:00 МСК.
