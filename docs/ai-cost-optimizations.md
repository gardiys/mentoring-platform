# Оптимизации расходов AI

Реализованы 8 сентября 2026 после [аудита расходов](ai-cost-audit-2026-09-08.md).

## Дополнение 21 сентября: кеш ответов и предварительные проверки

- Генерация и независимая проверка карточек используют один ключ запроса при чтении и сохранении кеша. Запрошенное имя модели хранится отдельно от фактического имени из ответа API: `gpt-5-mini` и возвращённый snapshot больше не мешают повторному использованию результата. Фактическая модель и расход сохраняются в финансовой истории.
- Ключ включает направление, провайдера, запрошенную модель, лимит вывода, версии промпта/схемы, источники и отправляемый вопрос после удаления личных данных и обрезки. Изменения отброшенного хвоста не вызывают новый запрос. Отменённые решения не используются; копии результатов кеша не возвращают в оборот отменённый оригинал.
- Формат ключа `answer-input-v2` не использует прежние неоднозначные ключи. Уже сохранённые контракты остаются на месте. При управляемой смене версии модели за тем же alias нужно повысить `ANSWER_CACHE_VERSION` либо изменить настройку на конкретный snapshot; удалять дату из имени модели для объединения разных версий нельзя.
- При включённой автопубликации до генерации и до независимой проверки выполняются проверки вопроса, решений модератора, возможных дублей и однозначной темы/колоды. Без подходящих источников автоматический черновик не генерируется. Причина сохраняется в истории; вопрос остаётся доступен для ручной обработки. Для режима shadow и обычной ручной модерации прежнее поведение сохранено.
- Отсутствие источников отмечается `needs_expert_source`; кластер без контракта может быть повторно рассмотрен после появления материалов. Повторная проверка не создаёт одинаковые события аудита. Прочие препятствия отмечаются `needs_manual_review`.
- Администратор по-прежнему может явно запросить AI-черновик существующей кнопкой, включая отложенный кластер. Такой запрос фиксируется как действие человека, не как одобрение ответа. Его задачи отделены от автоматических, а готовый ответ требует ручного решения. Независимая проверка по имеющимся источникам сохраняется.
- Финальная публикация повторяет проверки под блокировками: изменения модератора во время AI-запроса не обходятся. Полнота разбора интервью, промпты, модели и пороги качества не изменены.

Миграция БД не нужна. При развёртывании обновить backend и AI worker согласованно: явная генерация передаёт новый аргумент задачи `manual_draft`. Платные вызовы для проверки изменений не требуются — тесты используют поддельные провайдеры.

## Что работает автоматически

- Ключи кеша маршрутизации и проверки совпадений используют фактически отправляемый обрезанный текст, направление и версии модели/промпта/схемы. Различия в отброшенном хвосте больше не вызывают повторный запрос. Новый формат ключей не использует старые записи кеша; они остаются в истории решений.
- Точное совпадение с единственной доверенной опубликованной карточкой или подтверждённой формулировкой может заменить AI-классификацию. Это разрешено только для технического вопроса с уверенностью извлечения от 0,95, без проблем качества и признаков контекстной зависимости. Все исходные реплики вопроса должны присутствовать в транскрипте этого интервью и принадлежать говорящим, отличным от выбранного кандидата. При неизвестном авторстве AI-классификация сохраняется. Сохраняются ограничения направления, теневого режима, публикации и ручных изменений.
- Заведомо неоднозначное семантическое совпадение и другие не пройденные обязательные условия проверяются до вызова AI-судьи. Причина сохраняется в истории, вопрос продолжает обычную кластеризацию.
- Успешные фрагменты извлечения, отдельные оценки и частичные итоги сохраняются в `intelligence_ai_checkpoints` отдельной транзакцией. После сбоя они переиспользуются. Изменение входа, направления, разметки говорящих, промпта, схемы, модели или лимита вывода меняет ключ. Итоговая сборка вопросов остаётся атомарной. При удалении интервью его контрольные точки удаляются каскадно.
- Одинаковые тексты внутри одного запроса embeddings отправляются один раз; порядок и количество возвращённых векторов восстанавливаются для вызывающего кода.

Модели, промпты технического разбора, контекст перебиваний, перекрытие фрагментов и независимая проверка ответа карточки сохранены. Снижение reasoning и сокращение источников требуют отдельной проверки на реальных интервью и в эту версию не входят.

## Flex для фоновых задач

```dotenv
OPENAI_BACKGROUND_SERVICE_TIER=flex
OPENAI_FLEX_TIMEOUT_SECONDS=900
OPENAI_JOB_TIMEOUT_SECONDS=3600
OPENAI_MAX_RETRIES=0
```

Параметры передаются через оба Docker Compose файла. В локальном `.env` Flex включён; в `.env.production.example` приведён тот же вариант. Для существующего production `.env.production` нужно добавить параметры при развёртывании. Без параметра используется `default`.

Flex применяется к маршрутизации вопросов, проверке совпадений, генерации/валидации ответов карточек, карьерному пакету и оценке трудоустройства. Извлечение вопросов, оценки ответов и итог свежего интервью используют Standard; embeddings также используют обычный режим.

Для `gpt-5-mini` Flex имеет тарифы Batch: вход $0,125, кешированный вход $0,0125, выход $1 за миллион токенов — на 50% ниже Standard. Это скидка на переведённые запросы, а не гарантированное уменьшение общего счёта вдвое. Перед выбором другой модели нужно проверить поддержку Flex. [Тарифы](https://developers.openai.com/api/docs/pricing).

Flex может отвечать медленнее или возвращать `429 Resource Unavailable`. Воркеры используют существующие ограниченные повторы; автоматического перехода на более дорогой Standard нет. Таймаут задачи должен вмещать два последовательных Flex-запроса и ещё 60 секунд; несовместимая конфигурация отклоняется при создании OpenAI-провайдера. Для возврата к обычной обработке установить `OPENAI_BACKGROUND_SERVICE_TIER=default`. [Документация Flex](https://developers.openai.com/api/docs/guides/flex-processing).

Отдельная интеграция Batch API в этой версии не нужна для получения того же тарифа: используется Flex. Конвейер остаётся на существующей очереди ARQ.

## Учёт и развёртывание

Перед запуском обновлённого backend/AI worker применить миграцию `20260908_0084`:

```bash
# В окружении backend с настроенным DATABASE_URL:
alembic upgrade head
```

После обновления параметров пересоздать AI worker с новой конфигурацией. Старые задачи продолжаются через существующий механизм восстановления. Новые контрольные точки и журнал начинают заполняться после развёртывания; исторический расход не восстанавливается автоматически.

`ai_request_logs` сохраняет начало каждого прямого вызова, модель, режим обслуживания, request/response ID, признак восстановления, входные/кешированные/выходные/reasoning токены и оценочную стоимость. Usage сохраняется до разбора Structured Outputs, поэтому оплаченный невалидный JSON и первая попытка восстановления учитываются. Карьерные и employment-запросы используют тот же журнал. Он содержит финансовые метаданные без текстов интервью и сохраняется после удаления интервью.

Неизвестная цена или отсутствующий usage остаются `NULL`. Незавершённая попытка не считается бесплатной. Если после платного ответа запись usage в БД не удалась, метаданные попадают в журнал приложения; ошибка учёта сама по себе не запускает повторный платный запрос. При сбое между ответом провайдера и сохранением контрольной точки повтор запроса всё ещё возможен.

Оценка стоимости использует опубликованные 8 сентября 2026 тарифы `gpt-5-mini`/его snapshot и `text-embedding-3-small`; это не бухгалтерская сверка с OpenAI. Для неизвестной модели или режима стоимость не выдумывается. Метрики карточек используют эти тарифы, если старые ручные `OPENAI_*_PRICE_PER_MILLION_USD` не заданы; ручные ненулевые ставки сохраняют прежний приблизительный расчёт.

Посмотреть новый журнал за календарный день по Москве:

```bash
python -m app.scripts.report_ai_costs --date 2026-09-08
```

Без `--date` выводится текущий день. Команда только читает БД, не вызывает AI; группирует попытки по операции, модели и режиму, показывает токены, восстановление, ошибки, незавершённые попытки и неизвестную стоимость. Старые таблицы usage и история решений сохраняются, но суммировать их с новым журналом нельзя: успешные запросы могут присутствовать в обоих источниках.

## Проверки источников и накопленная очередь

- Набор источников закрепляется между генерацией, проверкой и публикацией;
  изменение ранжирования больше не вызывает ложный отказ или повторную проверку.
- Недоступные ссылки блокируются до обращения к модели. Изменение содержимого
  источника по-прежнему требует независимой проверки.
- Известные исторические отказы из-за выпавших ссылок восстанавливаются адресно:
  повторяется проверка сохранённого ответа, а не генерация. Ручные решения и
  прочие отказы остаются без изменений.
- Reconciler выбирает проверку готовых ответов перед генерацией новых и сдерживает
  продвижение старых теневых кластеров, пока текущая обработка не завершена.

Условия восстановления и порядок обновления описаны в `card-automation.md`.

## Очередь, общая пауза и тарифы (0089)

Кластеры с `needs_expert_source` без готового ответа исключены из основной
выборки 200 AI-задач. Reconciler отдельно проверяет материалы максимум для 50
таких кластеров за проход. Неудачная проверка назначает `source_retry_after`
через 6 часов и не вызывает AI. При появлении подходящего материала кластер
возвращается в обычную очередь. Явный ручной запуск черновика остаётся доступным;
решения человека периодическая проверка не переоткрывает.

Перед каждым запросом провайдер проверяет общую паузу в Redis для API-ключа
(в ключах Redis хранится только хеш) и модели. Первый 429 устанавливает паузу
по `Retry-After`/`retry-after-ms`, при отсутствии корректного заголовка — на
60 секунд. Параллельный 429 может продлить, но не сократить паузу. Другие модели
продолжают работать. Уже отправленные запросы не отменяются. Встроенные повторы
SDK отключены для запросов с общей паузой: повторами управляет ARQ.

Ожидающие задачи откладываются в Redis с небольшим случайным разбросом;
воркер не занимает слот ожиданием и не отправляет запрос. Такая отсрочка
возвращает использованную попытку ARQ, чтобы очередь не превращала ожидание
лимита в окончательную ошибку. Настоящие неудачные запросы по-прежнему имеют
ограниченный бюджет повторов. Ошибка квоты/оплаты не запускает этот механизм.
Если состояние паузы в Redis временно недоступно, новый запрос к AI не отправляется.
На ожидание не создаётся запись платного запроса.

Учёт стоимости дополнен семействами `gpt-5.6-terra` и `gpt-5.6-luna`, включая
датированные snapshots. Используются фактические `model` и `service_tier` из
ответа, токены обычного ввода, чтения кэша, записи кэша и вывода. Reasoning-токены
уже входят в output и повторно не начисляются. Поддержаны Standard, Flex,
Batch и Fast/priority; для GPT-5.6 ввод свыше 272 000 токенов учитывается по
тарифу длинного контекста. Версия тарифов: `openai-public-2026-09-22`.

Источники тарифов и полей usage:
[OpenAI API Pricing](https://developers.openai.com/api/docs/pricing),
[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching),
[обработка 429](https://developers.openai.com/api/docs/guides/error-codes).
Оценка относится к токенам запросов приложения; отдельные инструменты и
региональные надбавки в этом каталоге не рассчитываются.

Неизвестная модель/режим или неполная детализация остаются неизвестной стоимостью.
Для GPT-5.6 отсутствие `cache_write_tokens` не считается нулём. Старые строки
не переписываются по новым тарифам: без исходной детализации записи кэша
достоверный пересчёт невозможен. Дневной отчёт `app.scripts.report_ai_costs`
теперь показывает и сумму `cache_write_tokens`, отдельно от прочитанных токенов.

Обновление: применить миграцию `20260922_0089`, затем обновить backend и
`intelligence-ai-worker`. Настройки моделей и ключи менять не требуется.

## Дополнение 22 сентября: итог интервью и повторный разбор

По [аудиту production-расходов](research/interview-ai-cost-audit-2026-09-22.md)
реализованы первые два приоритета. Изменения требуют обновления backend,
AI-воркера и frontend; новых миграций нет.

Итог строится из уже сохранённых оценок. В него больше не передаются повторно
полные ответы кандидата и сгенерированные улучшенные ответы; доказательства
из рецензий сохраняются. Если вход укладывается в 45 000 символов, выполняется
один итоговый запрос. Для длинного интервью промежуточные запросы возвращают
компактные выводы с номерами вопросов по отдельной схеме, без полного отчёта,
приоритетных действий и повторных оценок коммуникации. Финальный отчёт создаётся
один раз по всем выводам и списку вопросов с исходными оценками и ограничениями.

Если промежуточная модель пропустила вопрос или сослалась на неизвестные номера,
сохраняется исходная рецензия. При невалидном сжатии используется исходный блок
оценок. Ошибки квоты и связи пробрасываются в штатную обработку повторов.
Успешные промежуточные результаты сохраняются как `summary_evidence` и не
оплачиваются повторно при сбое финального запроса.

Для полного итогового отчёта минимальный лимит вывода повышен до 8 000 токенов:
старые ответы регулярно обрезались на 4 000. Это потолок, а не фиксированная
оплата; промпт требует краткий результат. Более высокий настроенный лимит
сохраняется. Промпт итогового отчёта имеет новую версию, прежние итоги в кэше
не используются для новой схемы входа.

Обычный «Пересчитать AI-разбор» сохраняет checkpoints. Вопросы заново собираются
из сохранённого извлечения с применением текущих правил привязки реплик; AI
вызывается только при отсутствии подходящего результата. Ключ оценки больше
не зависит от нового UUID вопроса. Он по-прежнему зависит от интервью, вопроса,
ответа, контекста, направления, модели, промпта и схемы. Смена спикера меняет
вход извлечения; изменения текста и контекста инвалидируют соответствующие оценки.

Для полной новой генерации в панели администратора есть флажок «Полностью
пересчитать все этапы», передающий `force=true` в restart API. Он очищает
checkpoints. В обоих режимах сохраняются архив прежнего разбора, финансовая
история и опубликованные карточки; транскрибация повторно не заказывается.

Старые checkpoints оценок, созданные с UUID в ключе, не преобразуются автоматически:
после обновления первая такая оценка может потребовать нового запроса. Новые
результаты переиспользуются между ревизиями. Результаты разных интервью не смешиваются.
Изменения режима Flex, моделей и объёма технического фидбека в это дополнение не входят.

## Дополнение 22 сентября: технический фидбек, Flex и сравнение моделей (0091)

Оставшиеся три направления реализованы. Нужны миграция `20260922_0091` и
согласованное обновление backend, AI-воркера и frontend. `make prod-up` применяет
миграции перед запуском контейнеров. На рабочем сервере эти изменения пока не развёрнуты.

Технический фидбек использует промпт `technical-answer-review-v8-concise-scoring`:
краткий вывод, отдельные содержательные ошибки без повторения в нескольких
списках, улучшенный ответ только когда он нужен. Лимит вывода не уменьшен;
извлечение вопросов, исходные ответы и контекст для проверки авторства сохранены.
Текстовый промпт не гарантирует отсутствие всех повторов — это проверяется на примерах.
Проверенные полные ответы больше не требуют повторной генерации идеального ответа.
В ручном режиме карточек это может убрать необязательный AI-черновик; автопубликация
и раньше не считала такой черновик доверенным источником и продолжает независимую проверку.

Живое сравнение обнаружило путаницу между баллом за ответ и уверенностью модели:
`incorrect` иногда сопровождался баллом 1. Теперь смысл балла явно описан;
явные противоречия (`incorrect` с баллом > 0,5, `correct` с баллом < 0,5,
`unable_to_assess` с числовым баллом) не принимаются. Используется существующая
единственная попытка исправления структурированного ответа. Обе попытки учитываются
в расходах; после повторной ошибки результат не сохраняется как готовая оценка.

В панели повторного разбора появился флажок **«Экономичный разбор (Flex)»**.
API: `POST /api/v1/admin/interviews/ai-operations/{id}/restart?economy=true`;
`force` по-прежнему независимо управляет использованием сохранённых результатов.
Тариф хранится в интервью и виден в деталях. Новые интервью и обычный перезапуск
по умолчанию используют Standard. Настройка `OPENAI_BACKGROUND_SERVICE_TIER`
для карточек остаётся отдельной.

Flex использует те же модели, промпты и проверки, увеличенный таймаут
`OPENAI_FLEX_TIMEOUT_SECONDS` (900 секунд по умолчанию) и не переключается
самостоятельно на Standard. Требуется
`OPENAI_JOB_TIMEOUT_SECONDS >= 2 * OPENAI_FLEX_TIMEOUT_SECONDS + 60`.
Один проход задачи выполняет не более одной новой логической AI-операции
(максимум два запроса с учётом исправления структурированного ответа).
Готовые checkpoints не расходуют этот лимит. Затем задача сохраняет готовые
рецензии и продолжает со следующего этапа; штатное продолжение не расходует
бюджет неудачных попыток ARQ. Ошибки настоящих запросов остаются ограниченными
по числу повторов. Некорректное сжатие итогов во Flex завершается обычной ошибкой,
чтобы не возникал бесконечный цикл повторной оплаты того же блока.

Тариф изолирован через контекст конкретной задачи, поэтому параллельные разборы
не меняют режим друг друга. Переключение тарифа не обесценивает готовый результат
в кэше; изменение фактической модели, reasoning, промпта или входа обесценивает.
Старые технические оценки потребуют одного нового вызова после смены версии промпта.

Эксперименты с моделью и reasoning **выключены по умолчанию**:

- `OPENAI_REVIEW_REASONING_EFFORT=` — поведение основной технической модели без изменений;
  `low` включает эксперимент с меньшим reasoning. Не затрагивает извлечение и итоги.
- `OPENAI_SIMPLE_REVIEW_ENABLED=false` — переключение простых вопросов выключено.
- `OPENAI_SIMPLE_REVIEW_MODEL=` — модель для ограниченного перечня простых вопросов;
  при включении можно задать `gpt-5.6-luna` или проверенный snapshot.
- `OPENAI_SIMPLE_REVIEW_REASONING_EFFORT=low` — reasoning экспериментальной модели.

Маршрут использует точный небольшой список базовых вопросов, ограничение длины
ответа и исключение проблем атрибуции/транскрипции. Составные вопросы и сложные
темы остаются на основной модели. Это консервативное правило, а не детектор
всех возможных сложностей; перед включением требуется более широкая оценка качества.
Один общий выбор модели и reasoning используется и запросом, и ключом кэша.

Для воспроизводимой проверки добавлен скрипт, использующий только искусственные
примеры и локальный отчёт, без чтения или записи рабочей базы:

```sh
cd backend
# Показать набор примеров без запросов к API:
.venv/bin/python -m app.scripts.evaluate_interview_reviews
# Платное сравнение: 8 примеров, 3 варианта, максимум 48 запросов с учётом recovery:
.venv/bin/python -m app.scripts.evaluate_interview_reviews --live \
  --baseline-model gpt-5.6-terra --candidate-model gpt-5.6-luna \
  --output ../docs/research/interview-review-evaluation.json
```

Отчёт сохраняется после каждого результата, учитывает usage даже невалидных
ответов и останавливается при ошибке провайдера. Автоматическая проверка смотрит
на класс оценки, явные противоречия балла, наличие содержательного замечания и
лишнего идеального ответа. Она не заменяет чтение рецензий человеком.

[Результаты выполненного сравнения](research/interview-review-economy-2026-09-22.md)
содержат исходные ответы и расходы. Маленькая синтетическая выборка не доказывает
сохранение качества или такой же процент экономии на рабочих интервью.

Поведение Flex и варианты reasoning сверены с официальной документацией:
[Flex processing](https://developers.openai.com/api/docs/guides/flex-processing),
[GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna).
