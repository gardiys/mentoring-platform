# Оптимизации расходов AI

Реализованы 8 сентября 2026 после [аудита расходов](ai-cost-audit-2026-09-08.md).

## Дополнение 21 сентября: кеш ответов и предварительные проверки

- Генерация и независимая проверка карточек используют один ключ запроса при чтении и сохранении кеша. Запрошенное имя модели хранится отдельно от фактического имени из ответа API: `gpt-5-mini` и возвращённый snapshot больше не мешают повторному использованию результата. Фактическая модель и расход сохраняются в финансовой истории.
- Ключ включает направление, провайдера, запрошенную модель, лимит вывода, версии промпта/схемы, источники и отправляемый вопрос после удаления личных данных и обрезки. Изменения отброшенного хвоста не вызывают новый запрос. Отменённые решения не используются; копии результатов кеша не возвращают в оборот отменённый оригинал.
- Формат ключа `answer-input-v2` не использует прежние неоднозначные ключи. Уже сохранённые контракты остаются на месте. При управляемой смене версии модели за тем же alias нужно повысить `ANSWER_CACHE_VERSION` либо изменить настройку на конкретный snapshot; удалять дату из имени модели для объединения разных версий нельзя.
- При включённой автопубликации до генерации и до независимой проверки выполняются проверки вопроса, решений модератора, возможных дублей и однозначной темы/колоды. Без подходящих источников автоматический черновик не генерируется. Причина сохраняется в истории; вопрос остаётся доступен для ручной обработки. Для режима shadow и обычной ручной модерации прежнее поведение сохранено.
- Отсутствие источников отмечается `needs_expert_source`; кластер без контракта может быть повторно рассмотрен после появления материалов. Повторная проверка не создаёт одинаковые события аудита. Прочие препятствия отмечаются `needs_manual_review`.
- Администратор по-прежнему может явно запросить AI-черновик существующей кнопкой, включая отложенный кластер. Такой запрос фиксируется как действие человека, не как одобрение ответа. Его задачи отделены от автоматических, а готовый ответ требует ручного решения. Независимая проверка по имеющимся источникам сохраняется.
- Финальная публикация повторяет проверки под блокировками: изменения модератора во время AI-запроса не обходятся. Полнота разбора интервью, промпты, модели и пороги качества не изменены.

Миграция БД не нужна. При развёртывании обновить backend и AI worker согласованно: явная генерация передаёт новый аргумент задачи `manual_draft`. Платные вызовы для проверки изменений не требуются — тесты используют поддельные провайдеры.

## Что работает автоматически

- Ключи кеша маршрутизации и проверки совпадений используют фактически отправляемый обрезанный текст, направление и версии модели/промпта/схемы. Различия в отброшенном хвосте больше не вызывают повторный запрос. Новый формат ключей не использует старые записи кеша; они остаются в истории решений.
- Точное совпадение с единственной доверенной опубликованной карточкой или подтверждённой формулировкой может заменить AI-классификацию. Это разрешено только для технического вопроса с уверенностью извлечения от 0,95, без проблем качества и признаков контекстной зависимости. Все исходные реплики вопроса должны присутствовать в транскрипте этого интервью и принадлежать говорящим, отличным от выбранного кандидата. При неизвестном авторстве AI-классификация сохраняется. Сохраняются ограничения направления, теневого режима, публикации и ручных изменений.
- Заведомо неоднозначное семантическое совпадение и другие не пройденные обязательные условия проверяются до вызова AI-судьи. Причина сохраняется в истории, вопрос продолжает обычную кластеризацию.
- Успешные фрагменты извлечения, отдельные оценки и частичные итоги сохраняются в `intelligence_ai_checkpoints` отдельной транзакцией. После сбоя они переиспользуются. Изменение входа, направления, разметки говорящих, промпта, схемы, модели или лимита вывода меняет ключ. Итоговая сборка вопросов остаётся атомарной. При удалении интервью его контрольные точки удаляются каскадно.
- Одинаковые тексты внутри одного запроса embeddings отправляются один раз; порядок и количество возвращённых векторов восстанавливаются для вызывающего кода.

Модели, промпты технического разбора, контекст перебиваний, перекрытие фрагментов и независимая проверка ответа карточки сохранены. Снижение reasoning и сокращение источников требуют отдельной проверки на реальных интервью и в эту версию не входят.

## Flex для фоновых задач

```dotenv
OPENAI_BACKGROUND_SERVICE_TIER=flex
OPENAI_FLEX_TIMEOUT_SECONDS=900
OPENAI_JOB_TIMEOUT_SECONDS=3600
OPENAI_MAX_RETRIES=0
```

Параметры передаются через оба Docker Compose файла. В локальном `.env` Flex включён; в `.env.production.example` приведён тот же вариант. Для существующего production `.env.production` нужно добавить параметры при развёртывании. Без параметра используется `default`.

Flex применяется к маршрутизации вопросов, проверке совпадений, генерации/валидации ответов карточек, карьерному пакету и оценке трудоустройства. Извлечение вопросов, оценки ответов и итог свежего интервью используют Standard; embeddings также используют обычный режим.

Для `gpt-5-mini` Flex имеет тарифы Batch: вход $0,125, кешированный вход $0,0125, выход $1 за миллион токенов — на 50% ниже Standard. Это скидка на переведённые запросы, а не гарантированное уменьшение общего счёта вдвое. Перед выбором другой модели нужно проверить поддержку Flex. [Тарифы](https://developers.openai.com/api/docs/pricing).

Flex может отвечать медленнее или возвращать `429 Resource Unavailable`. Воркеры используют существующие ограниченные повторы; автоматического перехода на более дорогой Standard нет. Таймаут задачи должен вмещать два последовательных Flex-запроса и ещё 60 секунд; несовместимая конфигурация отклоняется при создании OpenAI-провайдера. Для возврата к обычной обработке установить `OPENAI_BACKGROUND_SERVICE_TIER=default`. [Документация Flex](https://developers.openai.com/api/docs/guides/flex-processing).

Отдельная интеграция Batch API в этой версии не нужна для получения того же тарифа: используется Flex. Конвейер остаётся на существующей очереди ARQ.

## Учёт и развёртывание

Перед запуском обновлённого backend/AI worker применить миграцию `20260908_0084`:

```bash
# В окружении backend с настроенным DATABASE_URL:
alembic upgrade head
```

После обновления параметров пересоздать AI worker с новой конфигурацией. Старые задачи продолжаются через существующий механизм восстановления. Новые контрольные точки и журнал начинают заполняться после развёртывания; исторический расход не восстанавливается автоматически.

`ai_request_logs` сохраняет начало каждого прямого вызова, модель, режим обслуживания, request/response ID, признак восстановления, входные/кешированные/выходные/reasoning токены и оценочную стоимость. Usage сохраняется до разбора Structured Outputs, поэтому оплаченный невалидный JSON и первая попытка восстановления учитываются. Карьерные и employment-запросы используют тот же журнал. Он содержит финансовые метаданные без текстов интервью и сохраняется после удаления интервью.

Неизвестная цена или отсутствующий usage остаются `NULL`. Незавершённая попытка не считается бесплатной. Если после платного ответа запись usage в БД не удалась, метаданные попадают в журнал приложения; ошибка учёта сама по себе не запускает повторный платный запрос. При сбое между ответом провайдера и сохранением контрольной точки повтор запроса всё ещё возможен.

Оценка стоимости использует опубликованные 8 сентября 2026 тарифы `gpt-5-mini`/его snapshot и `text-embedding-3-small`; это не бухгалтерская сверка с OpenAI. Для неизвестной модели или режима стоимость не выдумывается. Метрики карточек используют эти тарифы, если старые ручные `OPENAI_*_PRICE_PER_MILLION_USD` не заданы; ручные ненулевые ставки сохраняют прежний приблизительный расчёт.

Посмотреть новый журнал за календарный день по Москве:

```bash
python -m app.scripts.report_ai_costs --date 2026-09-08
```

Без `--date` выводится текущий день. Команда только читает БД, не вызывает AI; группирует попытки по операции, модели и режиму, показывает токены, восстановление, ошибки, незавершённые попытки и неизвестную стоимость. Старые таблицы usage и история решений сохраняются, но суммировать их с новым журналом нельзя: успешные запросы могут присутствовать в обоих источниках.
