# Повторный аудит расходов AI — 21 сентября 2026

После аудита по отдельному запросу реализованы приоритеты 1 и 2. Описание ниже фиксирует найденное до исправлений; текущее поведение и развёртывание описаны в [дополнении к оптимизациям](ai-cost-optimizations.md#дополнение-21-сентября-кеш-ответов-и-предварительные-проверки).

Проверены текущий код, разрешённые для вывода параметры локальной конфигурации, прежний аудит и официальная документация OpenAI. Выполнена локальная проверка ключей кеша без сетевых запросов. Рабочая база, журналы production и фактический счёт в этом аудите не запрашивались: доли расходов и общий процент экономии пока неизвестны. Изменений поведения приложения в рамках аудита нет.

Главная рекомендация: сначала исправить кеш ответов карточек и исключить заведомо бесполезную генерацию, затем измерять и сокращать контекст и reasoning. Смена модели для всего конвейера не является первым шагом.

## Что уже реализовано

- Сохранение успешных фрагментов извлечения, восстановления ответов, отдельных оценок и итогов интервью в `IntelligenceAICheckpoint`. Обычный повтор задачи после ошибки использует их.
- Кеш классификации и сопоставления карточек; проверка доверенных точных совпадений и обязательных условий сопоставления до платного запроса.
- Хранение embeddings у объектов; одинаковые тексты объединяются внутри одного запроса.
- Общий журнал `ai_request_logs`, включая cached input, reasoning, восстановление и невалидные ответы.
- Flex для классификации, сопоставления карточек, генерации и проверки ответов, карьерных материалов и оценки трудоустройства.

Локально extraction, analysis и light review настроены на `gpt-5-mini`; `OPENAI_BACKGROUND_SERVICE_TIER=flex`, вложенные SDK-повторы выключены. Это не подтверждает конфигурацию работающего сервера. Название light сейчас само по себе не означает более дешёвую модель.

Источники: [существующие оптимизации](ai-cost-optimizations.md), [провайдер](../backend/app/interviews/intelligence_ai.py), [контрольные точки](../backend/app/interviews/intelligence_checkpoints.py).

## Приоритет 1: исправить кеш генерации и проверки карточек

В `generate_cluster_candidate` и `validate_cluster_answer` есть воспроизводимое расхождение:

1. Поиск кеша использует `_analysis_model_name(provider)`: локально `gpt-5-mini`.
2. После ответа hash пересчитывается с `result.usage.model`.
3. `_usage` берёт имя модели из ответа API. При ответе `gpt-5-mini-2025-08-07` получается другой hash.
4. Дополнительно SQL-фильтр `_cached_answer_decision` требует точного совпадения `model_name`.

Если API возвращает snapshot вместо настроенного alias, одинаковый оплаченный результат не находится. Это касается обеих операций. Готовый контракт самого кластера по-прежнему предотвращает часть повторов; проблема не означает, что каждый проход очереди генерирует его заново.

Проверка действующими `_answer_input_hash` и `OpenAIInterviewAIProvider._usage`, с искусственным ответом API:

```text
generation: configured=gpt-5-mini, response=gpt-5-mini-2025-08-07, cache_key_matches=False
validation: configured=gpt-5-mini, response=gpt-5-mini-2025-08-07, cache_key_matches=False
```

Существующий тест повторного использования ответов использует `FakeInterviewAIProvider` и не проверяет расхождение alias/snapshot.

Есть и второй дефект: hash учитывает весь вопрос, но обе операции отправляют `question[:4_000]`. Локально подтверждено: разные отброшенные хвосты дают разные ключи при одинаковом отправленном вопросе.

**Предлагаемое решение:** единый построитель окончательного payload для отправки и кеша; отдельные поля идентичности запроса и фактически ответившей модели. Для предсказуемого обновления модели — закреплённый snapshot либо явная ревизия кеша при смене alias. Включать направление/область доступа, точный payload, версии промпта и схемы, настройки reasoning и вывода. Не объединять модели простым удалением суффикса даты: разные версии могут давать разные результаты. Старые записи переиспользовать только при доказанном соответствии модели и входа.

**Эффект:** каждый корректный cache hit исключает целый вызов, включая выход и reasoning. Частота таких повторов требует измерения. Риск изменения качества низкий при строгой идентичности входа.

Код: [поиск и запись кеша](../backend/app/interviews/card_automation_jobs.py), функции `generate_cluster_candidate`, `validate_cluster_answer`, `_cached_answer_decision`, `_answer_input_hash`; [чтение имени модели](../backend/app/interviews/intelligence_ai.py), `_usage`; [существующий тест](../backend/tests/test_card_automation_jobs.py), `test_identical_answer_inputs_reuse_persisted_generation_and_validation`.

## Приоритет 2: проверять возможность публикации до генерации

Сейчас при отсутствии источников генератор всё равно может запросить «best-effort» ответ. Затем `validate_cluster_answer` обнаруживает пустые источники и ставит `NEEDS_EXPERT_SOURCE` без AI-валидации. Такой черновик может быть полезен модератору, но автоматическую публикацию он обеспечить не может.

Другие проверки выполняются в `publish_validated_cluster` уже после генерации и независимой проверки ответа: наличие решения человека, пригодность исходных вопросов, уверенность, единственная подходящая тема/колода, возможные дубли.

**Предлагаемое решение:** для автопубликации сначала делать бесплатную предварительную проверку. Без источников или при заведомом препятствии оставлять понятную причину ручной обработки. Генерацию черновика для модератора при необходимости запускать отдельным действием. Проверки содержимого ответа и повторную проверку всех условий непосредственно перед публикацией сохранить — данные могут измениться во время AI-запроса.

**Эффект:** без источников исключается один запрос; при других заранее известных препятствиях потенциально исключаются генерация и валидация. Изменяется момент подготовки ручного черновика, поэтому это нужно учитывать в интерфейсе очереди.

Это особенно актуально после включения автосоздания: `recalculate_cluster_stats` при активной автопубликации переводит кластер к подготовке карточки без прежнего ожидания нескольких независимых интервью. Расход растёт с числом уникальных вопросов, даже при идеальном кеше. Это следствие нового поведения, а не само по себе ошибка.

Код: [генерация и обработка пустых источников](../backend/app/interviews/card_automation_jobs.py), [проверки публикации](../backend/app/interviews/card_auto_publish.py), [продвижение кластеров](../backend/app/interviews/card_automation_pipeline.py).

## Приоритет 3: уменьшить повторную передачу источников и данных итогового отчёта

`_trusted_sources` выбирает до восьми материалов и передаёт первые 8 000 символов каждого. Источники ранжируются по совпадениям слов в названии/описании; нужный абзац внутри документа специально не извлекается. Генерация и валидация могут получить до 64 000 символов источников каждая, без учёта служебных полей. Это предел в символах, не измеренное число токенов.

**Предлагаемое решение:** выделять релевантные разделы с устойчивыми идентификаторами и контекстом, сохранять единый снимок доказательств для генерации и валидации. Поиск сначала можно сделать локальным, без отдельного LLM-запроса. Число источников уменьшать только при сохранении покрытия ответа.

Отдельно `_summary_evidence_blocks` повторно передаёт ответ кандидата до 6 000 символов и `suggested_better_answer` до 4 000 символов на вопрос. Для общего отчёта можно проверить сокращённое представление: оценка, конкретные замечания, подтверждающие цитаты и признаки неопределённости. Начать с исключения развёрнутого образцового ответа; при сомнениях сохранять доступ к исходному ответу кандидата. Меньший вход также может уменьшить число промежуточных summary-запросов.

**Проверка качества обязательна:** оценка кандидата не должна превращаться в пересказ предыдущей оценки без доказательств. Нельзя экономить удалением перекрытий транскрипта, восстановления пропущенных ответов или независимой проверки публичной карточки.

Код: [источники](../backend/app/interviews/card_automation_jobs.py), `_trusted_sources`; [данные итогов](../backend/app/interviews/intelligence_jobs.py), `_summary_evidence_blocks`; [адресное восстановление ответов](../backend/app/interviews/intelligence_answer_recovery.py).

## Приоритет 4: использовать prompt caching осознанно

Инструкции уже стоят перед переменными данными, поэтому кеш OpenAI может работать и сейчас. `prompt_cache_key` явно не передаётся. Для используемой семьи моделей до GPT-5.6 документация рекомендует устойчивый ключ для запросов с общим префиксом; попадание в кеш не гарантируется. Источник: [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

Предложение: ключ по операции, версии промпта и направлению; одинаковый порядок источников и стабильная сериализация. Общие материалы размещать перед переменной частью там, где действительно есть повторяемый набор. Не включать случайный ID запроса в ключ. Измерить `sum(cached_input_tokens) / sum(input_tokens)` по операциям до и после. Не дополнять промпты бесполезным текстом ради порога кеша и не предполагать поддержку длительного retention без проверки конкретной модели.

Для `gpt-5-mini` Standard вход стоит $0,25, cached input — $0,025, выход — $2 за миллион токенов. Поэтому 90% скидки на кешированный вход — это не 90% скидки на весь разбор. В отличие от кеша результата, новый ответ всё равно генерируется. Источники: [тарифы](https://developers.openai.com/api/docs/pricing), [поведение кеша](https://developers.openai.com/api/docs/guides/prompt-caching).

## Приоритет 5: reasoning и оставшиеся операции Standard

Явный `reasoning.effort=low` сейчас задан только для карьерного пакета. Для маршрутизации и проверки совпадений стоит сравнить `low` с текущей конфигурацией на фиксированной выборке. Reasoning тарифицируется как выход; экономия зависит от фактических токенов, а снижение effort может ухудшить результат. Источник: [Reasoning](https://developers.openai.com/api/docs/guides/reasoning).

Извлечение, восстановление ответов, оценки и общий итог интервью остаются Standard: их операции отсутствуют в списке background в `_request`. Для массового переразбора старых интервью можно добавить отдельный Flex-режим. Для обычных пользовательских разборов сначала оценить допустимую задержку. Потребуется пересмотреть таймаут всей задачи: в ней последовательно выполняются несколько вызовов, а не один.

По текущим тарифам `gpt-5-mini` Flex стоит $0,125/$0,0125/$1 за миллион входных/кешированных/выходных токенов — половина Standard. Уже переведённые операции повторной экономии от этого не получат. Если подходящие Standard-операции составляют долю `f` текущих расходов, ориентир при неизменном числе токенов — `0,5 × f` от общего счёта, а не 50% всего счёта. Flex допускает задержки и временную недоступность; нужен управляемый повтор без незаметного перехода на дорогой режим. Источники: [тарифы](https://developers.openai.com/api/docs/pricing), [Flex](https://developers.openai.com/api/docs/guides/flex-processing).

Batch использует тот же тариф, что Flex: отдельная интеграция не добавит вторую скидку к уже работающему Flex. Рассматривать Batch стоит при иных требованиях к массовой обработке.

## Другие возможности

- **Адресный переразбор.** `prepare_analysis_restart` намеренно удаляет все checkpoint и вопросы, поэтому кнопка полного пересчёта платно повторяет этапы. Добавить отдельные режимы пересчёта оценок/итога и обработки только изменившихся входов, сохранив явный полный пересчёт для исправления неудачного результата. Для переиспользования неизменных оценок потребуется убрать случайный `question_id` из содержательной части ключа и корректно связывать результат с новыми объектами. Обычный retry уже кешируется — это другая операция.
- **Снимок источников.** `_publish_ready_cluster` сравнивает hash всего заново выбранного набора источников. Изменение набора сбрасывает проверку. Можно валидировать неизменный снимок доказательств и перед публикацией проверять актуальность и доступность его материалов. Простое игнорирование изменившихся нецитируемых документов небезопасно: они могли содержать противоречия, использованные проверяющим.
- **Оценка трудоустройства.** Дедупликация сейчас по клиентскому `idempotency_key`, не по содержимому. Новый ключ при том же профиле вызывает AI повторно. Добавить кеш точного безопасного payload, политики, модели и промпта в пределах дела; новые события или доказательства должны его инвалидировать.
- **Общий кеш embeddings.** Возможен кеш по тексту, модели и размерности между разными объектами и запросами. Сейчас есть кеш объекта и дедупликация внутри запроса. Приоритет ниже генерации текста: сначала проверить долю embeddings в счёте.
- **Ремонт формата.** `_parse_user_facing_response` при неверном языке или структуре повторяет всю оценку с увеличенным лимитом вывода. Для структурно корректного ответа с проблемой языка можно проверять исправление только нужных текстовых полей с сохранением исходной оценки. Для обрезанного/невалидного ответа такой путь не всегда применим. Не снижать вслепую `max_output_tokens`: обрезание может увеличить число платных повторов.

## Как измерить эффект

Начать с 7–14 дней production-данных из существующего read-only отчёта:

```bash
# В backend-окружении с нужным DATABASE_URL; дату выбирать явно.
python -m app.scripts.report_ai_costs --date 2026-09-21
```

Отчёт уже показывает расходы по операции/модели/режиму, input, cached input, output, reasoning, повторные попытки и неизвестные суммы. Не складывать его с прежними usage-таблицами: это задвоит часть расходов.

Доработать наблюдаемость: cache hit/miss по операциям, причины пропусков генерации, причины восстановления, длительность и устойчивый идентификатор интервью/кластера/ревизии без текста и персональных данных. В `AIRequestLog` привязки к сущности сейчас нет. Тогда можно считать цену успешного разбора и опубликованной карточки, а не только сумму по дню. Отдельно сверять Nexara и возможный внешний сервис Copilot — журнал прямых OpenAI-вызовов этого backend не равен всем расходам на AI.

Для массовой очереди полезен денежный бюджет с резервированием расходов выполняющихся задач и паузой новых запусков. Ограничение параллельности не уменьшает стоимость того же объёма работы; бюджет предотвращает неожиданный расход, но сам по себе не удешевляет запросы.

Проверка после изменений: cache hit при alias/snapshot и одинаковом фактическом входе; cache miss при изменении источника/модели/промпта; отсутствие AI при заведомой невозможности автопубликации; сохранение защиты от дублей и ручных решений. Для контекста/reasoning — отдельная выборка с ошибками спикеров, смешанными репликами, отрицаниями, длинными ответами и похожими, но различными техническими вопросами. Сравнивать полноту вопросов и ответов, авторство, оценки и ложные публикации вместе с ценой.
