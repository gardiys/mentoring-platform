# Критика реализации транскрибации через Soniox

Дата: 1 октября 2026.
Предмет: `backend/app/interviews/soniox_provider.py`, его подключение в
`intelligence_jobs.py`, настройки `SONIOX_*` в `app/core/config.py`,
`backend/app/check_soniox.py`, тесты `test_intelligence_soniox_provider.py` /
`test_transcription_provider_switch.py` / `test_soniox_deployment.py`,
раздел «Soniox и переключение транскрибации» в README.

Контекст: это продолжение [ревью транскрибации](transcription-review.md), которое
описывало Nexara. Для production Nexara пока остаётся выбором по умолчанию
(`.env.production.example` → `nexara`), локальная конфигурация переключена на Soniox.

Метод: чтение кода, тестов, настроек и документации. Прогонов на реальных записях
не было, поэтому численных утверждений о качестве распознавания здесь нет — их
отсутствие в проекте само является находкой (п. 5.6).

---

## 1. Вердикт

Адаптер сделан заметно лучше предыдущего: три из семи замечаний к транскрибации
закрыты, причём правильно. Но реализация вводит **три новых дефекта**, два из
которых серьёзнее того, что исправлено, и сохраняет самый дешёвый неиспользованный
рычаг качества — подсказку терминологии декодеру.

Главное: **миграция на нового вендора выполнена без единого измерения.** README это
признаёт прямо — «Гарантировать качество конкретной записи без прослушивания
нельзя». Решение «Soniox лучше Nexara» сейчас ничем не подтверждено, хотя оба
провайдера работают одновременно и инфраструктура для сравнения фактически готова.

---

## 2. Что исправлено относительно Nexara

| Было | Стало |
| --- | --- |
| `language=None`, автоопределение Whisper | `language_hints: ["ru","en"]` плюс `enable_language_identification` — ровно то, что нужно для code-switching |
| Только segment-level метки | Token-level timestamps всегда; язык определяется по токену и агрегируется по объёму текста |
| Сегменты копировались 1:1, без склейки | Сборка реплик из токенов: склейка по смене спикера, паузе >1500 мс и длине >30 с |
| Данные оставались у провайдера навсегда | `cleanup()` удаляет файл и расшифровку после сохранения |

Закрыты пункты 4.1 (язык), 4.5 (временные метки — частично) и 4.7 (пост-обработка —
частично) из [ревью транскрибации](transcription-review.md).

## 3. Что сделано сильно (не ломать)

- **Миграция между провайдерами спроектирована правильно.**
  [`_transcription(ctx, interview.transcription_provider)`](../../backend/app/interviews/intelligence_jobs.py#L1763-L1777) —
  ленивое создание адаптера по имени и кеш в контексте воркера. Задание,
  отправленное в Nexara, читается Nexara и после переключения настройки. README
  честно предупреждает хранить ключ прежнего провайдера до опустошения его очереди и
  прямо отрицает скрытую повторную платную отправку другому вендору.
- **`check_connection()`** — read-only проба через `/models`, проверяет и
  доступность, и наличие настроенной модели, без платной транскрибации.
  Доступна как `make check-soniox` / `make prod-check-soniox`.
- **`_identifier()`** валидирует UUID перед подстановкой в URL-путь: path injection
  в `transcriptions/{id}` невозможна.
- **Кросс-проверка** `transcript["id"] == provider_job_id`
  ([:273-274](../../backend/app/interviews/soniox_provider.py#L273-L274)) — защита от
  рассогласованного ответа.
- **`trust_env=False`** и явный прокси: ambient `HTTP_PROXY` / `HTTPS_PROXY` не
  подхватывается. Для прокси-зависимого вендора это верное решение, и README
  отдельно оговаривает, что SOCKS не поддерживается.
- **Умная обработка сбоя отправки**
  ([:239-249](../../backend/app/interviews/soniox_provider.py#L239-L249)): при
  неретраябельной ошибке загруженный файл удаляется, при ретраябельной —
  сохраняется, потому что задание могло быть принято.
- **Пунктуация без атрибуции наследует текущего спикера, а речь без атрибуции —
  нет** ([:88-90](../../backend/app/interviews/soniox_provider.py#L88-L90)).
  Аккуратное различение, которого обычно не делают.
- **Тела ответов не логируются** — с объяснением почему: они могут содержать имена
  файлов, URL и учётные данные.

## 4. P0 — критические

### 4.1. Диаризация не проверяется — регресс защитной позиции

Nexara-адаптер **отказывался работать** без диаризации:

```python
if not diarization:
    raise TranscriptionProviderError("TRANSCRIPTION_CONFIG_ERROR", ..., retryable=False)
```

Soniox-адаптер передаёт `enable_speaker_diarization: diarization`
([:206](../../backend/app/interviews/soniox_provider.py#L206)) и **не проверяет
результат**.

Если диаризация не сработала — не включена на проекте, не поддержана выбранной
моделью, отвалилась на стороне провайдера — все токены придут с `speaker=None`,
каждый алфавитно-цифровой токен станет `"unknown"`, и транскрипт схлопнется в
одного псевдо-спикера.

Дальше конвейер пройдёт целиком: админ выберет «кандидата» из единственного
`unknown`, extraction получит диалог без разделения ролей, ученик получит отчёт.
Никто не узнает, что разделения спикеров не было вовсе.

### 4.2. `"unknown"` протекает в домен как настоящий спикер

Тест
[test_unknown_speech_not_assigned_to_previous_speaker_and_pause_splits_turn](../../backend/tests/test_intelligence_soniox_provider.py#L184-L192)
фиксирует поведение как ожидаемое: `["2", "unknown", "unknown"]`.

`_save_transcript` создаёт `IntelligenceSpeaker` на каждый уникальный
`provider_speaker_key`, включая `unknown`. Значит он становится полноценной записью
спикера и появляется в списке выбора кандидата в админке. Реплики кандидата,
которым диаризация не присвоила метку, уходят в extraction под авторством, которого
не существует.

Это ровно тот класс проблем, под который написана вся машинерия `answer_spans` /
`speaker_attribution_conflict` / `answer_unreliable` — только теперь источником
становится сам адаптер, а не провайдер.

### 4.3. Запись остаётся у Soniox после любого терминального сбоя

`cleanup` вызывается **только на успешном пути**, после `_save_transcript` и
`commit` ([jobs.py:523-530](../../backend/app/interviews/intelligence_jobs.py#L523-L530)).

Хуже: `cleanup()` сам упадёт на провалившемся задании. Внутри он вызывает
`self._job(data)`, а тот **бросает исключение** для статуса `error`
([:181-187](../../backend/app/interviews/soniox_provider.py#L181-L187)) — до строки
`if ... is not COMPLETED: return`. На ERROR-задании очистка не просто не
выполняется, она невозможна этим методом.

Пути, после которых запись остаётся у вендора:

- задание завершилось статусом `error`;
- невалидный ответ (`TRANSCRIPTION_INVALID_RESPONSE`);
- истёк дедлайн опроса (по умолчанию 6 часов);
- `_save_transcript` упал;
- воркер умер между коммитом и вызовом cleanup.

README описывает это мягче, чем есть: «После сбоя сети при отправке или очистке
удалённые объекты могут остаться: их можно проверить в Soniox Console». Фактически —
после **любого** терминального сбоя, и единственное предложенное средство — ручная
инспекция консоли.

Речь идёт о записях собеседований реальных людей: голос, имя, место работы, детали
проектов. Нужен периодический sweeper, а не инструкция смотреть в консоль.

## 5. P1 — существенные

### 5.1. Мерцание диаризации теперь напрямую раздувает число реплик

Сборка делает `flush()` на **каждой** смене спикера
([:91-96](../../backend/app/interviews/soniox_provider.py#L91-L96)). Ложная
последовательность A→B→A внутри одного монолога даёт три utterance вместо одной.

Сглаживания коротких вставок нет — это задача 7.2 из
[ревью транскрибации](transcription-review.md), и она остаётся открытой. В
результате архитектура стала чувствительнее к ошибкам диаризации, чем была:
extraction работает окнами по 40 реплик с перекрытием 8, поэтому раздувание числа
реплик бьёт дважды — по цене и по числу разрывов «вопрос в одном окне, ответ в
следующем».

### 5.2. Синхронное чтение файла в async-загрузке

```python
with file_path.open("rb") as source:
    uploaded = await self._request("POST", "files", files={"file": (..., source, ...)})
```

Обычный файловый объект отдаётся `httpx.AsyncClient` — чтение идёт синхронно в event
loop воркера. Для видео до 2 ГБ это держит loop занятым на всё время аплоада, а тот
же воркер параллельно опрашивает другие задания. Нужен `anyio.open_file` либо чтение
в thread pool.

### 5.3. Константы сборки реплик не обоснованы и не проверены

`1500` мс пауза, `30_000` мс максимум, условие
`parts[-1].rstrip().endswith((".", "?", "!"))`. Не настраиваются, нигде не
объяснены, влияние на качество не измерено.

Третье условие опирается на то, что последний токен — знак препинания. У Soniox
пунктуация приходит отдельными токенами, поэтому правило отработает только в этом
случае, а при другой токенизации тридцатисекундный предел просто не сработает. Это
недокументированная зависимость от внутреннего поведения провайдера.

### 5.4. `extra="ignore"` молча глотает всё полезное

`_Token` читает `text`, `start_ms`, `end_ms`, `speaker`, `language`. Всё остальное
отбрасывается без следа
([:23-29](../../backend/app/interviews/soniox_provider.py#L23-L29)).

Soniox отдаёт по токену уверенность распознавания — стоит проверить в реальном
ответе API, но если она там есть, она сейчас теряется. А это именно то, что нужно
для **объективного** признака `bad_transcription`: сейчас его ставит языковая модель
по тексту, а снимает другая языковая модель, которая транскрипта не видела (см.
[card-automation-review.md](card-automation-review.md), п. 4.4). Числа для этого
решения, возможно, уже приходят — и выбрасываются здесь.

Структурная проблема шире: при обновлении API проект не узнает, что появилось
что-то ценное.

### 5.5. Глоссарий по-прежнему не передаётся в запрос

Async API Soniox поддерживает передачу доменного контекста для смещения
распознавания. 33 термина из `intelligence_transcript_context.py` (GIL, goroutine,
WaitGroup, GOMAXPROCS, мьютекс, дедлок) используются **только** как whitelist
пост-фактум исправлений, причём исправление принимается лишь если ошибочный вариант
буквально присутствует в списке произношений.

Самый дешёвый неиспользованный рычаг: подсказать терминологию декодеру стоит одно
поле в запросе, а исправлять постфактум — лишние токены в каждом вызове extraction
и 95 % отброшенных предложений модели.

### 5.6. Два провайдера, ноль сравнительных данных

`.env.production.example` → `nexara`. Локальный `.env` → `soniox`, причём
`TRANSCRIPTION_PROVIDER` объявлен в нём **дважды** (строки 35 и 95) — результат
зависит от порядка парсинга dotenv.

Переключатель сделан технически грамотно, инфраструктура для A/B фактически готова:
два работающих адаптера, выбор по интервью, учёт в
`IntelligenceTranscriptionUsage`. Не хватает только замера — эталонного набора и
WER / DER / flip rate (волна 0 из [ревью транскрибации](transcription-review.md)).
Без него нельзя ответить, стало ли лучше, и нельзя обосновать перевод продакшена.

## 6. P2 — средние

- **Маппинг `409 → TRANSCRIPTION_NOT_READY retryable`**
  ([:154](../../backend/app/interviews/soniox_provider.py#L154)) спекулятивен: async
  API отдаёт готовность полем `status` с кодом 200. Не вредно, но вводит в
  заблуждение следующего читателя.
- **`duration_ms` может быть вычислен, а не получен**: при отсутствии или
  невалидности `audio_duration_ms` берётся `max(item.end_ms ...)`
  ([:276-278](../../backend/app/interviews/soniox_provider.py#L276-L278)). Это
  основа учёта расходов — стоит помечать источник значения, иначе сверка с биллингом
  вендора будет расходиться необъяснимо.
- **`check_connection` проверяет только наличие модели**, но не то, что она
  поддерживает диаризацию и нужные языки. При ошибке в `SONIOX_MODEL` проба скажет
  OK, а диаризации не будет — см. п. 4.1.
- **Нет отдельного лимита на загрузку через Files API** — проверяется только общий
  `interview_video_max_bytes` = 2 ГБ.
- **Подготовка аудио по-прежнему отсутствует**: видео уходит в STT целиком, теперь
  ещё и через загрузку файла. Извлечение аудиодорожки через `ffmpeg` сократило бы и
  трафик, и время, и расход у вендора (задача 8 из
  [ревью транскрибации](transcription-review.md)).

## 7. Безопасность

В `.env` лежат два живых ключа — `SONIOX_API_KEY` и `NEXARA_API_KEY`.

`.env` находится в `.gitignore` и git его не отслеживает — в репозиторий ключи не
попали, это проверено.

Тем не менее ключ Soniox был выведен в ходе анализа и попал в транскрипт сессии.
**Рекомендуется ротация в Soniox Console.** Файл к тому же открывается в IDE: при
шаринге экрана или скриншотах это прямая утечка.

## 8. Что делать по порядку

1. **Проверять результат диаризации** (4.1): если доля токенов без спикера выше
   порога или распознан единственный спикер — не продолжать конвейер, а переводить
   интервью в «транскрибация требует проверки». Это восстанавливает защиту, которая
   была у Nexara-адаптера.
2. **Не пускать `unknown` в домен как спикера** (4.2): помечать такие реплики
   отдельным признаком вместо создания `IntelligenceSpeaker`, и показывать админу,
   сколько речи осталось без атрибуции.
3. **Sweeper для брошенных данных у провайдера** (4.3): периодическая задача,
   удаляющая файлы и задания по всем интервью в терминальных статусах; заодно убрать
   падение `cleanup()` на ERROR-задании.
4. **Читать уверенность токена** (5.4) и считать из неё объективный
   `bad_transcription` — это закрывает и находку из ревью карточек.
5. **Передать глоссарий в запрос** (5.5) — одно поле, самый дешёвый выигрыш по
   качеству.
6. **Сгладить мерцание** (5.1) и вынести константы сборки в настройки (5.3).
7. **Замерить оба провайдера** на эталонном наборе (5.6) — и только после этого
   переводить продакшен.

Шаги 1-3 стоит выполнить **до** перевода продакшена на Soniox: первый и второй
позволяют молча потерять разделение ролей, третий оставляет записи людей у третьей
стороны.
