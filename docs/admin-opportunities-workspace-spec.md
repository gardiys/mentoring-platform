## 2. Что не так: диагноз

### 2.1. Ввод итога консультации роняет страницу

Воспроизведено тестом. Консультация в статусе `paid` или `scheduled` → набрать третий символ в поле
«Краткий письменный итог» → React Router заменяет страницу экраном ошибки:
`TypeError: Cannot read properties of null (reading 'value')` в `AdminOpportunitiesPage.tsx:531`.

Причина: обработчик читает `event.currentTarget.value` внутри функционального апдейтера
`setConsultationDrafts((current) => …)`. React обнуляет `event.currentTarget` сразу после
обработчика, а апдейтер иногда выполняется позже, во время рендера. Первые символы проходят, дальше
страница падает. Вставка всего текста одним действием иногда срабатывает, поэтому баг выглядит
плавающим.

Тот же дефект в этом файле: строка 497 («Комментарий администратора», в тесте падает у
запланированной консультации), 675 (дата встречи), 822 («Комментарий к решению» по заявке на Go,
падает). Ещё 36 таких мест в 9 других админских формах (этап 1.3), там дефект может проявляться
так же.

Следствие: завершить консультацию можно только с итогом не короче 10 символов, а набрать его
нельзя. Поэтому оплаченные и запланированные консультации остаются незакрытыми.

### 2.2. Тупики: заявку нельзя довести до конца

| Ситуация | Почему тупик |
|---|---|
| Оплата консультации попала в `manual_review` (например, ученик оплатил старую, уже отозванную ссылку) | Консультация остаётся `payment_pending`. Новую ссылку ученик получить не может (`payment_requires_manual_review`). У админа только «Отменить». Эндпоинт `POST /admin/opportunities/payments/{attempt_id}/confirm` есть, но UI его не вызывает, а dashboard не отдаёт попытки оплаты. |
| Оплаченная консультация не состоялась (неявка, ментор заболел) | Переходы `paid → cancelled` и `scheduled → cancelled` запрещены. |
| Нужно сменить ментора после одобрения | Ошибка `consultation_mentor_locked`. |
| В сохранённом итоге ошибка | После `completed` поле только для чтения, хотя бэкенд допускает `completed → completed`. |
| Заявка на Go одобрена, ученик не оплатил за 14 дней | Checkout отвечает `legal_application_expired`, статус навсегда остаётся `approved` (или `payment_pending`). Новую заявку ученик подать не может («У вас уже есть заявка на переход в Go»). У админа нет кнопок. |
| Встреча прошла, консультацию не закрыли | Об этом никто не узнаёт: нет напоминаний и нет признака просрочки в UI. |

### 2.3. Уведомлений нет

- Консультации и Go не создают ни одного уведомления — ни админу, ни ученику, ни ментору.
- Повтор Python уведомляет админов только в колокольчике (`_notify_admins`), без Telegram.
- У пункта меню «Возможности» нет счётчика: о новой заявке можно узнать, только открыв страницу.
- Всё нужное уже есть: `create_notification` (колокольчик опрашивается каждые 30 с) и
  `queue_telegram_message` (outbox доставляется каждые 15 с; личные сообщения по `user.telegram_id`
  — так уже работают напоминания о платежах в `jobs.py`).

## 4. Этап 1 — hotfix

### 1.1. Падение при вводе

Во всех четырёх обработчиках `AdminOpportunitiesPage.tsx` (строки ≈497, 531, 675, 822) считывай
значение до вызова setState:

```tsx
onChange={(event) => {
  const value = event.currentTarget.value;
  setConsultationDrafts((current) => ({
    ...current,
    [item.id]: { ...draftOf(current, item), summary: value },
  }));
}}
```

`draftOf` — необязательный хелпер вместо четырёх копий сборки черновика. Главное — не обращаться к
`event` внутри апдейтера.

### 1.2. Утечка черновика итога

- «Запланировать» отправляет `written_summary: item.written_summary`, а не черновик.
- Бэкенд: в ответах ученику (`opportunities_dashboard`) `written_summary` равен `null`, пока статус
  не `completed`. Админские ответы не меняются.

### 1.3. Тот же дефект в других формах

Отдельным коммитом исправь все места, которые находит правило ниже, и добавь его в
`frontend/eslint.config.js` (блок для `**/*.{ts,tsx}`):

```js
"no-restricted-syntax": [
  "error",
  {
    selector:
      "CallExpression[callee.name=/^set[A-Z]/] > ArrowFunctionExpression MemberExpression[property.name='currentTarget']",
    message:
      "Считайте event.currentTarget до вызова setState: внутри апдейтера он уже null.",
  },
],
```

На коммите `2ecf0717` правило находит 40 мест в 10 файлах: `AdminOpportunitiesPage.tsx` (4),
`AdminInterviewCardEditPage.tsx` (6), `AdminRoadmapEditPage.tsx` (5), по 4 —
`AdminStudentForm.tsx`, `AdminTrackForm.tsx`, `AdminInterviewDeckEditPage.tsx`,
`AdminKnowledgeEntryEditPage.tsx`, `AdminKnowledgeTopicEditPage.tsx`, `AdminMentorsPage.tsx`,
и 1 — `AdminMentorPayoutsPanel.tsx`. Затронуты и чтения `.checked` у переключателей.

### 1.4. Понятная причина неактивной кнопки

Под полем итога — счётчик `N / 10 000` и, пока символов меньше 10, подсказка «Ещё N символов, чтобы
завершить». `maxLength`: итог — 10 000, комментарий — 5 000 (как в `AdminConsultationMutation`).

### 1.5. Тесты

- Новый `frontend/tests/admin-opportunities.test.tsx`. Консультация `paid`: `userEvent.type`
  набирает 40 символов в итог и 20 в комментарий. Заявка на Go `submitted`: 20 символов в
  комментарий. Страница не падает, значения остаются в полях. «Завершить с итогом» вызывает
  `api.updateAdminConsultation` с `status: "completed"` и введённым итогом. «Запланировать» не
  отправляет черновик итога.
- Backend: ученик не видит `written_summary` у `scheduled` и видит у `completed`.

Готово, когда тесты зелёные, `pnpm lint` проходит с новым правилом, а консультация закрывается с
итогом, набранным с клавиатуры.

## 5. Этап 2 — уведомления и счётчики

### 2.1. Этапы заявки

Добавь на бэкенде по одной чистой функции на продукт. По заявке она возвращает `stage`,
`next_action` (текст для админа), `waiting_since` и `overdue`. Это единственный источник правды для
счётчиков, сводки, очереди и карточки: фронтенд ничего не выводит из статусов сам.

Консультации:

| Статус | Условие | `stage` | Следующий шаг | `waiting_since` | Ждёт админа |
|---|---|---|---|---|---|
| requested | — | `new` | Назначить ментора и выставить счёт | `created_at` | да |
| payment_pending | последняя попытка оплаты в `manual_review` | `payment_review` | Проверить оплату | время попытки | да |
| payment_pending | иначе | `awaiting_payment` | Ждём оплату от выпускника | — | нет |
| paid | — | `needs_schedule` | Согласовать время встречи | `paid_at` | да |
| scheduled | конец встречи в будущем | `scheduled` | Встреча {дата} | — | нет |
| scheduled | `scheduled_at + duration_minutes` уже прошло | `needs_completion` | Внести итог и закрыть | конец встречи | да |
| completed | — | `completed` | — | — | нет |
| cancelled | — | `cancelled` | — | — | нет |

Python → Go:

| Статус | Условие | `stage` | Следующий шаг | Ждёт админа |
|---|---|---|---|---|
| submitted | — | `new` | Рассмотреть заявку | да |
| approved, payment_pending | срок условий не истёк | `awaiting_student` | Ждём подтверждения и оплаты до {дата} | нет |
| approved, payment_pending | `terms_expires_at` прошёл, оплаты нет | `expired` | Продлить условия или отменить заявку | да |
| paid | — | `enrolled` | Зачислен в Go | нет |
| rejected, cancelled | — | `closed` | — | нет |

Повтор Python (черновики админу не показываются вовсе):

| Статус и условие | `stage` | Следующий шаг | Ждёт админа |
|---|---|---|---|
| submitted | `new` | Начать рассмотрение | да |
| under_review | `review` | Принять решение | да |
| needs_diagnostic, needs_clarification | `awaiting_student` | Ждём ответ выпускника | нет |
| approved, terms_accepted, payment_pending | `awaiting_payment` | Ждём принятия условий и оплаты | нет |
| paid или enrolled, у зачисления нет ментора | `needs_mentor` | Назначить ментора | да |
| есть оффер в статусе `submitted` | `offer_review` | Проверить оффер | да |
| enrolled, остальное | `active` | — | нет |
| rejected, cancelled, expired | `closed` | — | нет |

Просрочка (`overdue`), пороги — константами в модуле: `new` дольше 24 ч; `needs_schedule` дольше
48 ч; `needs_completion` — через 2 ч после конца встречи; `payment_review` и `expired` — сразу; у
повтора Python `new`, `review` и `offer_review` дольше 48 ч, `needs_mentor` дольше 24 ч.

### 2.2. Уведомления админам

Получатели — все активные пользователи с ролью `admin`. Каналы:

- колокольчик: `create_notification`, kind `status_changed` (как у повтора Python, без миграции
  enum);
- Telegram: личное сообщение через `queue_telegram_message(chat_id=admin.telegram_id, …)` с кнопкой
  `telegram_action_url(link)`, если у админа заполнен `telegram_id`.

Уведомление создаётся в той же транзакции, что и событие.

| Событие | Где возникает | Текст | Ссылка |
|---|---|---|---|
| Новая заявка на консультацию | `create_consultation` | «Новая заявка на консультацию»: имя и @username ученика, формат, выбранный ментор или «любой», начало брифа до 300 символов | `/admin/opportunities?consultation={id}` |
| Консультация оплачена | `approve_opportunity_payment`, переход в `paid` | «Консультация оплачена — согласуйте время» | то же |
| Оплата требует проверки | каждое место, где `OpportunityPaymentAttempt` становится `manual_review`: `approve_opportunity_payment` и ветка webhook в `payments/router.py` | «Оплата требует проверки» + продукт и ученик | карточка заявки своего продукта |
| Новая заявка на переход в Go | `create_go_transition` | «Новая заявка на переход в Go» + имя и начало мотивации | `/admin/opportunities?go={id}` |
| Повтор Python: новая заявка, новый оффер | существующий `_notify_admins` | без изменений, добавить Telegram | `/admin/opportunities/python-repeat?application={id}` |

Ссылки сразу делай в итоговом формате. Параметр карточки заработает на этапе 3, до этого страница
его просто игнорирует.

Идемпотентность: `create_notification` сам дописывает `user_id` к ключу события, а
`queue_telegram_message` — нет. Ключ Telegram-сообщения должен содержать id админа
(`telegram:consultation-requested:{id}:{admin_id}`), иначе второй админ сообщения не получит.

Все переходы попытки оплаты в `manual_review` проведи через один хелпер, который меняет статус и
уведомляет админов.

### 2.3. Ежедневная сводка

Новая cron-задача в `NotificationWorkerSettings` по образцу `schedule_payment_reminders`. В
`notification_reminder_hour` по `notification_reminder_timezone` (по умолчанию 10:00 по Москве)
каждый админ получает одно сообщение в колокольчик и Telegram, если есть просроченные заявки:
«Ждут действия: 2 новые заявки дольше суток, 1 консультация прошла и не закрыта…» со ссылкой на
`/admin/opportunities`. Ключ события содержит дату, повторный запуск в тот же день дубля не создаёт.
Нет просрочек — нет сообщения.

- Функции этапов — табличный тест по всем строкам таблиц 2.1, включая границы порогов.
- Заявка на консультацию создаёт уведомление каждому активному админу и строку `telegram_outbox`
  каждому админу с `telegram_id`. Неактивный админ ничего не получает. Повторный вызов с тем же
  ключом не создаёт дубля.
- Переход оплаты в `manual_review` уведомляет админов.
- Сводка учитывает только просроченное; закрытые и отменённые заявки в неё не попадают; второй
  запуск в тот же день не создаёт дублей.
- `summary`: числа совпадают с данными; ученик и ментор получают 403.
- Фронтенд: бейдж в меню показывает число.

## 6. Этап 3 — рабочее место

### 3.1. Команды вместо PATCH со всем состоянием (консультации)

Замени `PATCH /admin/opportunities/consultations/{id}` командами. Каждая команда:

- блокирует строку (`with_for_update`);
- проверяет исходный статус и все условия до изменения полей (сейчас `admin_update_consultation`
  меняет поля раньше проверки `paid_at`);
- пишет историю (3.3) и шлёт уведомления (3.4);
- возвращает карточку `AdminConsultationDetail` (3.5), а не весь dashboard.

| Команда | Из статусов | Тело | Результат |
|---|---|---|---|
| `POST …/consultations/{id}/approve` | requested | `mentor_id`, `message_to_student?` | `payment_pending`; ментор проверяется через `_mentor_options`, как сейчас |
| `POST …/{id}/reject` | requested | `reason` (10–2000 символов, видит ученик) | `cancelled` |
| `POST …/{id}/mentor` | requested, payment_pending, paid, scheduled | `mentor_id` | смена ментора с проверкой `_mentor_options`; вознаграждение получит тот, кто назначен в момент завершения |
| `POST …/{id}/schedule` | paid, scheduled | `scheduled_at` (с часовым поясом) | `scheduled`; повторный вызов — перенос |
| `POST …/{id}/complete` | paid, scheduled | `written_summary` (10–10 000), `held_at?` | `completed`; если `scheduled_at` пуст, сохранить в него `held_at`; ровно одно `MentorReward`, как сейчас |
| `PATCH …/{id}/summary` | completed | `written_summary` | правка итога без нового начисления |
| `POST …/{id}/cancel` | payment_pending, paid, scheduled | `reason`; `refund_required` (обязателен, если была оплата) | `cancelled`; pending-попытки оплаты → `revoked`; вознаграждение не создаётся; при `refund_required` админам уходит «Оформите возврат» |
| `PATCH …/{id}/internal-note` | любой | `internal_note` (до 5000) | только для админов |
| `POST …/payments/{attempt_id}/confirm` | уже существует | — | вызывается из карточки для попытки в `manual_review`; дальше работает `approve_opportunity_payment` |

Сообщения ученику (`message_to_student`, `reason`) храни в существующем `admin_note` — ученик уже
видит его как «Комментарий команды». Новое поле `internal_note` (3.3) не попадает ни в один ответ
ученику.

Когда фронтенд переведён на команды, удали старый PATCH (им пользуется только
`AdminOpportunitiesPage`) и перегенерируй `frontend/src/api/generated/schema.ts`
(`make api-generate` при запущенном бэкенде). Новые типы на фронтенде бери из `Schemas[...]`, а не
описывай вручную.

### 3.2. Python → Go

- `POST …/go-transition/{id}/approve` и `POST …/go-transition/{id}/reject` (`reason`) вместо
  `PATCH …/go-transition/{id}`.
- `POST …/go-transition/{id}/cancel` (`reason`) из `approved` и `payment_pending`. После отмены
  ученик может подать новую заявку.
- `POST …/go-transition/{id}/extend` для заявки в `expired`: заново зафиксировать текущие условия
  (`_go_transition_terms_snapshot()` и версия), `terms_expires_at = now + 14 дней`, статус не менять.
- `cancel` и `extend` запрещены, пока у заявки есть попытка оплаты в `pending`, `approved` или
  `manual_review` либо действующий legal checkout (`legal_checkouts.status = 'pending'` и
  `expires_at` в будущем). В UI показать причину. Логику legal checkout не менять.

### 3.3. Данные и миграция

Одна новая ревизия Alembic после `20261016_0100`:

- `consultation_request_history` и `go_transition_application_history` по образцу
  `python_repeat_application_history`: `old_status`, `new_status`, `actor_user_id`, `comment`,
  `snapshot` (JSONB с изменёнными полями), `created_at`. Пишутся из всех команд и из обработки оплаты
  (`actor_user_id = null`). Без backfill: для старых заявок карточка показывает известные даты
  (`created_at`, `paid_at`, `completed_at`) как события истории.

- Индексы под фильтры, если их требуют планы запросов: `consultation_requests (mentor_id)`,
  `consultation_requests (status, scheduled_at)`.
- `alembic heads` показывает один head; downgrade удаляет только добавленное.

### 3.4. Уведомления ученику и ментору

Каналы — колокольчик и Telegram (если есть `telegram_id`), как в 2.2. Время в Telegram — в
`notification_reminder_timezone` с подписью зоны («19:00 МСК»). Формулировки нейтральные, без
обращения, как `status_titles` у повтора Python.

| Событие | Кому | Текст | Ссылка |
|---|---|---|---|
| Консультация одобрена | ученик | «Консультация подтверждена — можно оплатить» + сообщение админа | `/opportunities/alumni/consultations` |
| Заявка отклонена или отменена | ученик | с причиной; при `refund_required` — что деньги вернут | то же |
| Назначено или перенесено время | ученик, ментор | дата, время, длительность; ментору — ещё формат, имя и @username ученика, бриф | ученику — то же; ментору — без ссылки (своей страницы у ментора нет, см. этап 4) |

### 3.5. API для интерфейса

- `GET …/admin/opportunities/inbox?product=&q=&page=&page_size=` → `{items, total, counts}`.
  Элемент: `product`, `id`, `student` (id, имя, @username, email), `title` (формат или продукт),
  `status`, `stage`, `next_action`, `waiting_since`, `key_date`, `overdue`. Только то, что ждёт админа;
  сначала просроченное, затем по `waiting_since` от старых к новым. Объёмы малы (десятки заявок),
  поэтому собирать можно в Python, но выбирать из БД только статусы, которые могут ждать админа, без
  архива.
- `GET …/admin/opportunities/consultations?group=&mentor_id=&consultation_type=&q=&page=&page_size=`
  → `{items, total, counts}`. Группы: `active` (по умолчанию — всё, кроме `completed` и
  `cancelled`), `needs_action`, `waiting` (ждём выпускника или встречу), `completed`, `cancelled`,
  `all`. Поиск — по имени, фамилии, @username, email и id.
- `GET …/admin/opportunities/consultations/{id}` → `AdminConsultationDetail`: всё из списка плюс
  бриф, условия, ментор с @username, сообщения ученику, `internal_note`, последняя попытка оплаты
  (`attempt_id`, `status`, `created_at`), история.
- Аналогично `…/go-transition` и `…/go-transition/{id}`. Для повтора Python — фильтры и пагинация у
  существующего списка и отдельный detail с историей из `python_repeat_application_history`.
- Настройки — `GET …/admin/opportunities/settings` (тарифы, менторы-консультанты, описание Go).
  Прежний `GET …/admin/opportunities` удалить вместе со старым UI.
- Студенты и менторы — join'ами, без N+1; пагинация на сервере, по умолчанию 25 строк.

### 3.8. Карточка заявки (Drawer)

Шапка: имя ученика; «Написать в Telegram» (`https://t.me/<username>`); email с кнопкой копирования;
«Профиль ученика» (`/admin/students/<id>/edit`); бейдж статуса и крупно — следующий шаг.

Консультация, сверху вниз:

1. Запрос: формат, бриф (с переносами строк), ментор, которого выбрал ученик.
2. Условия: цена, вознаграждение ментору, длительность.
3. Ментор: имя, @username, кнопка «Сменить» (команда `mentor`).
4. Оплата: статус последней попытки; при `manual_review` — предупреждение и «Подтвердить оплату».
5. Панель действий текущего этапа с одной главной кнопкой (таблица ниже).
6. «Сообщения выпускнику» — отправленные сообщения и причины с пометкой «видит выпускник».
7. «Внутренняя заметка» — отдельное поле с кнопкой сохранения и пометкой «видят только
   администраторы».
8. История.

| `stage` | Главное действие | Дополнительно |
|---|---|---|
| `new` | ментор (предвыбран выбор ученика, только включённые консультанты) и необязательное «Сообщение выпускнику» → «Одобрить и выставить счёт» | «Отклонить» — модальное окно с обязательной причиной |
| `awaiting_payment` | нет; показать, когда создана ссылка на оплату, или «ещё не открывал оплату» | «Отменить заявку» с причиной |
| `payment_review` | «Подтвердить оплату» с подтверждением | «Отменить» |
| `needs_schedule` | дата и время (`datetime-local` с подписью часового пояса) → «Назначить время» | «Отметить проведённой» → форма итога; «Отменить» |
| `scheduled` | дата встречи и «Перенести» | «Завершить» → форма итога; «Отменить» |
| `needs_completion` | форма итога раскрыта сразу: «Итог для выпускника» (видит выпускник; 10–10 000 символов; счётчик; подсказка «рекомендации и план») и «Когда прошла встреча» (по умолчанию — время встречи) → «Завершить консультацию» | «Не состоялась» → отмена |
| `completed` | итог только для чтения и «Исправить итог» | — |
| `cancelled` | причина отмены и признак возврата | — |

Отмена оплаченной консультации: в окне — причина и обязательный выбор «Нужен возврат денег» или
«Без возврата».

Заявка на Go: мотивация, зафиксированные условия, срок условий. Действия: `new` → «Одобрить» или
«Отклонить» (с причиной); `expired` → «Продлить на 14 дней» или «Отменить»; `awaiting_student` →
«Отменить»; `enrolled` → подсказка «Назначьте Go-ментора в профиле ученика» со ссылкой.

Требования к формам:

- Состояние формы живёт в компоненте карточки и сбрасывается при смене заявки. Общий словарь
  черновиков на всю страницу не нужен.
- Отдельный хук мутации на каждую команду; `loading` и блокировка только у кнопок этой карточки.
- После успеха — сообщение об успехе, обновление списка и счётчиков; карточка остаётся открытой и
  показывает новый этап.
- Подтверждения с причиной — `Modal` из `@mantine/core` (пакета `@mantine/modals` в проекте нет);
  простые подтверждения — как принято в проекте.
- Клиентская проверка длины текста совпадает с серверной.
- На мобильном Drawer открывается на весь экран, кнопки действий закреплены внизу.

### 3.13. Тесты этапа 3

Backend:

- Каждая команда: допустимые и запрещённые исходные статусы, 403 для ученика и ментора, запись в
  историю, уведомления из 3.4.

  вознаграждения; смена ментора до завершения — вознаграждение новому ментору.

- Go: отмена освобождает ученика для новой заявки; продление обновляет снимок условий и срок, после

Frontend:

- Для каждого `stage` консультации видна правильная главная кнопка и вызывается правильный метод API.
- Ссылка `?consultation=<id>` открывает карточку; закрытие убирает параметр.
- «Отклонить» требует причину; отмена оплаченной требует выбора про возврат.

- Повтор Python: черновиков нет, подписи переведены.
- Регрессионные тесты этапа 1 переносятся на новые компоненты.

- Все новые эндпоинты — только для `AdminUser`.
- `internal_note`, `mentor_reward_kopecks` и попытки оплаты никогда не попадают в ответы ученику.
- Даты только с часовым поясом; схемы отклоняют naive datetime (как уже сделано у повтора Python).
- Уведомления — через outbox в той же транзакции; из обработчика запроса Telegram API не вызывать.
- Новую логику консультаций и Go можно вынести из `service.py` (больше 1100 строк) в отдельные
  модули — без циклических импортов.

## 9. Проверка и сдача

Из корня репозитория:

```bash
make lint
make format-python-check
make test
python -m unittest discover -s scripts -p 'test_*.py'
graphify update .   # или .local/bin/graphify update .
```

Backend-тесты используют локальную PostgreSQL `mentoring_test` (см. `AGENTS.md`). После изменения
схем API — `make api-generate` при запущенном бэкенде.

Ручной сценарий на dev-данных (`make seed`):

1. Выпускник оставляет заявку на консультацию → у админа уведомление в колокольчике, строка в
   `telegram_outbox`, бейдж в меню показывает 1.
2. Из уведомления открыть карточку → одобрить с ментором → ученик получает «можно оплатить».
3. Оплатить через dev-эндпоинт → админ получает «Консультация оплачена» → назначить время → ученик
   и ментор получают время встречи.
4. Перевести время встречи в прошлое → заявка в «Нужно сделать» как «Нужно закрыть» → набрать итог
   с клавиатуры (50+ символов) → «Завершить» → ученик видит итог, у ментора одно начисление.
5. «Исправить итог» → начисление не задвоилось.
6. Заявка на Go → одобрить → перевести `terms_expires_at` в прошлое → «Продлить» → ученик может
   оплатить. В другой ветке — «Отменить» → ученик подаёт новую заявку.
7. Попытка оплаты в `manual_review` (оплатить старую ссылку после создания новой) → «Проверить
   оплату» → «Подтвердить» → консультация `paid`.
8. Открыть раздел на ширине 375 px и из Telegram Mini App: карточка на весь экран, «Назад»
   закрывает её.

Отчёт — `docs/admin-opportunities-workspace-report.md`.

## 10. Открытые вопросы и решения по умолчанию

1. Отмена оплаченной консультации разрешена с причиной и выбором «нужен возврат» или «без
   возврата». Возврат оформляется вручную вне платформы; вознаграждение ментору при отмене не
   начисляется.
2. Telegram-уведомления админам — личными сообщениями каждому. Если нужен общий админский чат,
   добавить настройку чата и темы по образцу `telegram_interview_*` и слать туда.
3. Ментор получает сообщение в Telegram с контактами ученика при назначении времени. Кабинет
   ментора — этап 4.
4. Сводка о зависших заявках — раз в день в 10:00 по Москве (`notification_reminder_hour`).
